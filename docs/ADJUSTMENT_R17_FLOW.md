給 Codex 執行。執行前依 AGENTS.md §10 讀取 `AGENTS.md`、`docs/CODEX_INSTRUCTIONS.md`、`docs/REQUIREMENTS.md`、`docs/ROADMAP.md`、`docs/USER_GUIDE.md`、`docs/REVIEW_STATE_CONTRACT.md`、`docs/REVIEW_MD_CONTRACT.md`、`docs/ADJUSTMENT_R11_SIMPLIFY.md`。分析器、graph schema、API 狀態推導規則（D4／D5、R-API-1～6）本輪不改。R3–R16 的「不要做」與「停止條件」仍適用，但**本輪明確取代**的功能（§2）不受先前輪次保留要求的約束。

## 0. 需求方的要求與結論

> 實際測試後，操作還是太複雜。從頭討論，聚焦在 ScreenTrace 的主要流程功能。

主要流程只有一條：

```text
分析專案 → 打開報表 → 在畫布上看畫面、點按鈕試操作 → 標記保留／移除 → 進度自動存成 md → 把 md 交給 AI
```

需求方已確認的決定（2026-10-11 討論）：

| 編號 | 決定 |
|---|---|
| R17-1 | 報表只剩兩頁：**畫面**、**API**。盤點首頁、逐頁確認頁、按鈕總表、功能地圖頁、交付清單頁全部取消，能力併入這兩頁或移除。 |
| R17-2 | 移除**信心狀態**、**元件樣式**、**元件庫**相關功能。**只從報表與 md 移除**，分析器與分析產物（`application-graph.json`、`preview-model.json` 等）保留不動。這是需求方對 REQUIREMENTS §1「分析畫面中所有元素的樣式」與 D3（元件庫匯入）在報表呈現上的暫緩決定，REQUIREMENTS 原文不改。 |

### WP61　兩頁版面

```text
[畫面]  [API]                      已確認 23/78 ▾   ● 已自動儲存   [下載 md]  [?]
┌ 搜尋 URL／名稱 ──┐ ┌──────── 畫布 ────────┐ ┌ 右側欄 ───────────┐
│ [清單｜檔案結構] │ │                       │ │ 畫面名稱  URL      │
│ 全部／未確認／   │ │                       │ │ [保留][移除][未確認]│
│ 保留／移除       │ │                       │ │ 按鈕（預設收合）   │
│ 畫面列表…        │ │                       │ │ API                │
└──────────────────┘ └───────────────────────┘ │ 從哪些畫面可來到這 │
                                               └────────────────────┘
```

1. **頂部列**：頁籤「畫面｜API」、進度標籤（點擊展開：保留／移除／未確認數量、衝突數量，點數量可篩選左側清單）、存檔狀態（WP65）、「下載 md」、「?」。
2. **左側欄**：一個搜尋框，同時搜尋實際 URL（沿用既有 URL 對路由樣板、星號、副檔名映射比對）與畫面名稱；結果在清單與畫布同步高亮。清單／檔案結構切換；狀態篩選晶片（全部／未確認／保留／移除）。點清單項目＝在畫布上 zoom in 該畫面。
3. **右側欄**（未選畫面時顯示「點選畫布上的畫面開始確認」）：
   - 畫面名稱、URL、三段式選擇器（`radiogroup`，方向鍵切換）。
   - 「按鈕」：該畫面可標記的元件清單，**預設收合**，每列一組三態小按鈕；畫面標移除時元件顯示「隨畫面移除」。頁首／頁尾片段按鈕收在群組內（沿用既有規則）。
   - 「API」：該畫面呼叫的 API，點擊切到 API 頁並選取該筆。
   - 「從哪些畫面可來到這裡」：來源畫面清單，點擊 zoom 到該畫面。
   - 衝突提示（保留元件導向移除畫面等）：有才顯示。
   - 分析提示（JSF 未分析、context path 等）：有才顯示，一行文字。
4. **「?」浮層**：快捷鍵、操作方式、狀態圖例（保留／移除／未確認）、「ScreenTrace 看不到的事」。
5. 鍵盤：`k` 保留、`x` 移除、`u` 未確認（作用於目前畫面，或右側欄中聚焦的按鈕）；`n` 下一個未確認畫面；輸入欄位內不觸發。

驗收：頂部列可見控制項 ≤ 6；只有兩個頁籤；搜尋實際 URL 能找到對應畫面（沿用既有 URL 搜尋 fixture）；1024px 寬不溢出；全部可鍵盤到達。

### WP62　畫布 zoom in 聚焦

取代目前「點畫面開啟另一個聚焦板、目標畫面重新排在四周」（`relations.ts` 的 `focusLayout`）的做法。

1. **畫布狀態**：沿用目前畫布排版與卡片。滑過卡片的高亮行為保留。
2. **點畫面 A**：鏡頭以約 400ms 平滑動畫平移並 zoom in 到 A（`prefers-reduced-motion` 下直接切換），A 放大成**完整畫面預覽**（沿用現有預覽與截圖資料），其他畫面淡出隱藏。
3. **關聯線**：只顯示**從 A 出發**的關聯線，每條線的方向就是原畫布上 A 指向目標畫面的方向，從 A 的邊緣延伸到視窗邊緣。同方向多條線以扇形略為錯開，每條可單獨滑過、單獨點擊、可鍵盤聚焦（Tab 依序、Enter 前往）。
4. **滑過關聯線**：顯示目標畫面的縮圖、名稱、URL，以及觸發這條線的按鈕名稱；同時在 A 的預覽中高亮該按鈕。
5. **點關聯線**：鏡頭移動並 zoom in 到目標畫面 B（B 成為焦點，A 隱藏）。
6. **目的地無法確定的出口**（動態組成網址等，靜態分析找不到目標畫面）：畫一條短虛線，滑過顯示「無法確定前往哪個畫面」與觸發按鈕；不可點擊前往。
7. **返回**：Esc、左上「返回畫布」按鈕、滾輪縮小到低於焦點比例時，zoom out 回完整畫布，並保留原本的平移位置。
8. **`n`**：鏡頭移到下一個未確認畫面（依左側清單順序）並 zoom in。
9. **瀏覽器上一頁**：zoom 歷史沿用既有記憶體歷史（`prototype-history.ts`），不寫入網址。
10. 畫布上已決定的畫面卡片顯示狀態色條與圖示（沿用 R11 WP40）；卡片上的滑過標記按鈕移除，標記統一在右側欄或快捷鍵。

驗收（E2E）：點卡片後只有 A 可見；可見關聯線集合＝原畫布上 `from=A` 的關聯集合（逐條比對 `data-from`／`data-to`）；每條線的角度與原畫布 A→目標 中心連線角度差 ≤ 15°；滑過顯示縮圖；點線後焦點為目標；虛線數＝`focusedRelations` 中 unresolved 的觸發數；Esc 回到原平移位置；`n` 跳到下一個未確認。

### WP63　模擬操作＝真實點擊

1. zoom in 後，在 A 的預覽中點擊連結、按鈕、送出：
   - 唯一目標畫面：等同點擊對應關聯線，zoom 到目標畫面。
   - 多個候選：在點擊位置附近列出候選畫面（名稱＋縮圖），選一個前往。
   - 彈窗：顯示示意內容（沿用 WP26）。
   - 呼叫 API 但不換頁：顯示一行提示「呼叫 API：<URL>」，點擊可切到 API 頁。
   - 目標無法確定：顯示「無法確定前往哪個畫面」。
2. 表單送出**不做資料檢核**：不顯示檢核提示、不攔截；示例值輸入欄位保留可輸入，但不影響結果。
3. 刪除 Alt 點擊只選取、觸控長按、首次脈動外框。滑過可互動元素仍顯示外框與手指游標。
4. 候選集合與目標畫面必須與既有模擬 fixture 的結果完全相同（只改呈現，不改 `simulate` 的計算）。

驗收：既有模擬 fixture 逐項比對目標與候選；含必填檢核的表單送出直接前往目標；不存在檢核提示元素。

**WP62、WP63 完成後停止**，等需求方檢視外觀與手感。

### WP64　API 頁簡化

1. 單一清單，欄位：API（方法＋公開 URL）、處理程式（類別.方法）、呼叫來源數、狀態。
2. 狀態三種：**使用中**（含原「推定使用中」）、**未被使用**（D5，無呼叫來源）、**可移除**（D4，全部呼叫來源皆被標移除）。推導函式不改，只在呈現層把兩種使用中合併。
3. 搜尋框＋狀態篩選＋排序（URL、狀態、來源數）。
4. 點一筆展開：呼叫來源列表（畫面＋按鈕），點來源切回畫面頁並 zoom in 該畫面、高亮該按鈕。
5. 刪除：畫面網址切換、契約、前端請求描述、URL 別名區塊。

驗收：共用向量 `docs/examples/api-usage-vectors.json` 兩端測試仍通過；呈現層的三態對照有單元測試。

### WP65　進度檔自動存檔

先做 **spike**：在 Chrome（目前穩定版）以 `file://` 開啟的報表中，驗證 `showSaveFilePicker`、`showOpenFilePicker`、檔案 handle 存入 IndexedDB、重新開啟後 `requestPermission` 是否可用。**若任何一項在 `file://` 下不可用，停止本工作包**，把實測結果寫入 OPEN_QUESTIONS，不得改用本機伺服器或其他方案。

1. **第一次標記時**：右上存檔狀態顯示「尚未設定進度檔」並彈出提示「選擇進度檔的存放位置」，預設檔名 `screentrace-review-<應用名稱>.md`。使用者取消時照常標記（存瀏覽器暫存），存檔狀態維持「尚未設定」，可隨時點擊設定。
2. **之後每次標記**：約 500ms 去抖動後寫入整份 md（格式見 WP66）。狀態顯示「● 已自動儲存」／「儲存中…」／「⚠ 儲存失敗（點此重試）」。寫入失敗不得遺失記憶體中的決策。
3. **重新開啟報表**：若 IndexedDB 有上次的 handle，頂部顯示「繼續上次進度：<檔名>」，點一下取得授權並載入；也可點「開啟其他進度檔」選擇。載入時驗證分析指紋；不同時沿用既有「分析結果已變更」與 orphan 提示。
4. **瀏覽器暫存**（localStorage）同時寫入，作為 Chrome 以外瀏覽器與授權被拒時的備援；兩者不一致時以使用者選擇載入的進度檔為準。
5. **不支援 File System Access API 的瀏覽器**：存檔狀態顯示「此瀏覽器不支援自動存檔，請用『下載 md』保存」，「開啟進度檔」改用 `<input type=file>`。
6. 「下載 md」永遠可用，下載內容與進度檔相同。
7. 零網路請求維持。

驗收：Playwright Chromium 以 `file://` 實測：設定進度檔 → 標記 → 檔案內容更新；關閉並重開頁面 → 繼續上次進度 → 決策還原；寫入失敗模擬 → 記憶體決策保留且顯示重試；不支援 API 的環境（以腳本移除 API 模擬）退回下載／上傳。

### WP67　CLI 一步完成

1. `./bin/screentrace <專案路徑>`（Windows 同）：直接分析該路徑，完成後自動開啟報表。結果寫入 `<分析結果根目錄>/<專案資料夾名稱>/`；未設定結果根目錄時使用預設值（`<ScreenTrace 根目錄>/analyze/`），**不強制首次設定**。
2. 不帶參數時維持現有選單；首次啟動若未設定專案根目錄，選單第一項改為「輸入專案路徑」，設定根目錄改為選用（`screentrace config`）。
