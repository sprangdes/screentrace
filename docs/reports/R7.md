- View as XML：`vets/vetList.jsp:38` 的圖行為為 NAVIGATE，指向已確認的 `GET /vets.xml`；`VetController.java:58` 為資料回應端點，只有 HANDLED_BY，後續沒有 RENDERS／FORWARDS_TO 通向 SCREEN。
- View as JSON：`vets/vetList.jsp:41` 指向已確認的 `GET /vets.json`；`VetController.java:51` 同樣只有資料處理鏈，沒有可證明的目的畫面。

這裡的「目的未解析」指**模擬的畫面／操作結果無法證明**，不是 URL 未解析。沒有把資料回應當畫面，也沒有改為 CALL_API 或執行請求。

實際以 file:// 開啟 WP29 petclinic 報表（1440×900）：Home → Welcome、Find owners → Find Owners、Veterinarians → Vet List、Error → Exception 均仍可切換。再點 View as XML／JSON，兩次均留在 Vet List，結果文字為「靜態分析無法確認這個操作」，並補「已記錄行為但無法確認結果：行為目的未解析，沒有可證明的目的畫面或操作結果」。右欄同步顯示此原因，計算樣式／來源仍收合；Vet List 的分類為無行為 1、目的未解析 2。實際檢視截圖確認原因在預覽上方與右欄清楚呈現，未顯示分類英文列舉，預覽仍在同屏。分析抽屜顯示全專案兩層中文分類。eMusic 也實際開啟，分類為 72＋15。兩頁 pageerror 與額外網路請求皆為 0；觀察 JSON／截圖只留 /private/tmp，不提交。

### WP29 失敗測試、完整驗證與決定性

先提交 733518b：自行撰寫的 petclinic 風格 JSON 向量與新測試。舊實作三個分類／契約測試 0 通過、3 失敗，原因是沒有 assessSimulation／unmappedReason 及不拒絕非法欄位。Java reader 的新增測試也先失敗於未保留 unmappedReason，再補實作。追加點選一致性測試先發現右欄缺少彈窗 DOM 上下文（誤標未知原因，1 != 0），再統一元素判定入口，確認可開啟彈窗與原生輸入不被誤標。沒有改任何既有斷言；本輪新增測試的路徑修正使用模組相對 URL，E2E 僅精確選取可見右欄，避免與抽屜統計的同名定位衝突。

最終完整驗證：268 Java、40 JS、80 viewer unit、41 capture、79 Chromium E2E，全部通過，零失敗／略過。新增不變量覆蓋 petclinic 風格合成資料、原 WP26 fixture、四種 WP10 family；每個畫面與全專案原因加總等於無法確認總數。真實兩專案逐畫面／全專案亦檢查加總成立。capture 每個列舉一例；Java／viewer 驗證未知分類及錯誤適用範圍被拒絕。安全／往返／API／決定性／WP10 golden 全保留。

### 字型載入時序的決定性回歸

本輪最初兩次真實分析一致；補強點選判定後再次重驗，petclinic 的 Vet List 出現不一致：圖與 packed documents 相同，但部分導覽文字高度 19px／18px、寬度、styleId 不同，HTML 為 3,612,265／3,624,020 bytes。不能以最初一致結果掩蓋這次失敗。

capture 原本在 domcontentloaded 後立即量測，字型可能仍在載入。先提交合成失敗測試 fc8f9c6（實際狀態 loading），再觸發版面並在 Node 端等待每個 FontFace 載入完成或失敗，5 秒逾時沿原 capture 診斷處理。沒有固定成功延遲、沒有改寫 computed styles，也不執行目標程式。頁面 JavaScript 停用時，FontFaceSet.status／頁面輪詢回呼不能可靠完成；新增測試初稿改為檢查各 FontFace 的實際狀態，並用不含等待的舊模組副本再確認測試失敗，沒有修改任何本輪之前的既有斷言。詳 ADR0055。

修正後重新完整驗證，兩專案在三個獨立輸出目錄各完整分析三次，四份輸出全部一致；上述失敗差異消失。成功載入由 petclinic 真實字型驗證，失敗後 fallback 由自行撰寫且攔截的合成字型驗證；未下載或提交第三方字型／目標資料。來源雜湊、路徑掃描、畫面及全專案分類加總、實際導覽與 XML／JSON 提示再次確認。沒有放寬圖、證據、決定性或安全斷言。
