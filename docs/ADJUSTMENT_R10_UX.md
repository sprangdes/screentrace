## 0. 目標

需求方要的是：**用最簡單直覺的方式，清楚知道被分析專案有哪些功能、流程、按鈕，並能有效率地完成「功能確認」（保留／移除／未確認）。**

目前的報表已能看畫面圖、試操作、標記，但從需求方的角度仍有明顯落差：

1. **只有「畫面圖」，沒有「功能」層級。** 需求方用「功能」思考（找飼主、新增飼主、獸醫列表），報表只呈現一堆畫面卡片與連線。
2. **看不到「專案共有哪些按鈕、各自做什麼」。** 按鈕只能一個畫面一個畫面點開看；要確認 68 個按鈕得逐畫面操作。
3. **確認缺少全局掌握。** 沒有整體進度、沒有「下一個未確認」、標記要點選下拉或小按鈕、不知道標記「移除」會連帶影響什麼、匯出前沒有檢查摘要。
4. **流程只能看線。** 線團難讀，沒有「從這裡出發會經過哪些畫面、點哪個按鈕」的文字化大綱。
5. **搜尋只認 URL 與路徑**，不認按鈕文字、API 路徑。
6. **第一次使用沒有引導**，需求方不知道從哪開始。
7. **回歸缺陷（最優先）**：見 §1。

## 1. 先修的回歸缺陷（WP34）

審查者在 petclinic 重新分析後，總覽一開啟工具列顯示「流程 49／全站導覽 0／全部 49」，所有導覽線都畫成流程線，總覽又變成線團。R5 時同一專案是「流程 14／全站導覽 36／全部 49」。

**根因（已讀程式確認）**：`screentrace-viewer/src/overview.ts` 的 `navigationKey()` 用 `JSON.stringify([to, node.name, 全部屬性依序])` 判定「同一個全站導覽項目」。R7（WP27）在每個由 tag 展開的元件加入了 `attributes.expansionAnchor`（每個元件唯一），於是每個導覽元件的鍵都不同，永遠湊不到「≥2 個畫面且 ≥50% 畫面擁有相同導覽項目」，分類全部失效。R7 當時的測試 fixture 沒有帶錨點的導覽元件，因此未發現。

要求：
1. `navigationKey()` 改為只納入**語意上決定「同一個導覽項目」的屬性白名單**（例如 `tag`、`kind`、`componentType`、`href`／`target`、`httpMethod`、可見名稱），並明確排除來源／溯源類屬性（`expansionAnchor`、來源檔、行號、元件 ID 等）。白名單寫成具名常數並附註解說明理由。
2. 盤點 viewer 內所有「比較整個 `attributes`」或以全屬性序列化當鍵的地方（搜尋 `JSON.stringify`、`attributes` 全等比較），逐一確認是否同樣受錨點影響；有則修正，並在報告列出清單。
3. **先提交失敗測試**：fixture 含 4 個畫面，每個畫面都有 3 個經 tag 展開、帶有**各自不同** `expansionAnchor` 的相同導覽項目（同名同目的），斷言它們被分類為全站導覽，且畫面特有連結仍為流程。同時保留既有 R5 的分類測試。
4. 以 petclinic 唯讀重新分析驗證：預設應回到「流程 14／全站導覽 36／全部 49」（數字以實際輸出為準寫入報告），並附一張**合成 fixture** 重拍的 `overview-global-nav.png`（不得使用 petclinic 圖）。

WP34 完成後**停止**，等需求方確認再進 WP35。

## 2. 預先授權（同 R4 §0）

只可修改**直接鎖定被取代的版面結構或措辭**的斷言；鎖定資料正確性、證據、安全、決策保存規則、md 往返、決定性、API 狀態推導的斷言一律不得修改。每處在新 ADR 逐處記錄並證明新斷言在舊實作上失敗。無法歸入者寫 OPEN_QUESTIONS 並停止該項。

## 3. 硬性原則

1. **只改呈現與互動**。不改分析器、graph schema、API 狀態推導、md 格式、決策保存格式與 key。新增的視圖全部由**既有圖與既有決策**在 viewer 內推導。
2. **不猜**。分組、流程、影響預覽只能用已有的證據推導；推導規則必須機械、可說明，並在介面上標示依據（例如「依 URL 路徑前段分組」）。無法歸類者放入明確的「其他」組，不丟棄。
3. **決策模型不變**：畫面與元件各自三態，元件決策以（畫面,元件）為鍵。新增的批次操作只是對既有鍵逐一寫入，必須與單筆操作產生**逐位元組相同**的 md。
4. 單一 HTML、離線、決定性、不含本機路徑；報表大小增幅相對 R9 結束時不超過 8%。
5. 所有新增文字為需求方語言；不出現內部代號與未翻譯列舉。

## 4. 工作包

### WP35　功能區域總覽（看懂「有哪些功能」）

1. 左側欄「地圖｜檔案結構」旁新增第三個模式「功能」。依下列**機械規則**把畫面分組成「功能區域」：
   - 優先依 handler 所屬的控制器類別（Spring）或 Action 路徑前綴（Struts）；沒有 handler 資訊時，退而依主要 URL 路徑的第一段（`/owners/**` → 「owners」）；根路徑 `/` 與無路由者歸入「首頁與其他」。
   - 區域名稱由分組鍵人性化（駝峰／連字號拆字，沿用 R5 的命名函式），並在區域標題旁小字標示分組依據（「依控制器」或「依網址前段」）。
   - 分組演算法為單一純函式，決定性、可單元測試，並以測試鎖定。
2. 每個區域顯示一張摘要卡：區域名稱、畫面數、按鈕數、使用到的 API 數、**確認進度**（已確認／總數的比例條，確認模式關閉時顯示為灰階提示）。區域內列出其畫面（名稱＋URL）。
3. 點區域 → 地圖只顯示該區域的畫面，區域外的相連畫面以「→ 其他區域：名稱」的小標籤接在邊界上（不畫遠線）；有「顯示全部」可還原。
4. **畫面摘要行**：每個畫面的標題下方加一行機械產生的摘要，例如「可前往 4 個畫面 · 9 個按鈕 · 呼叫 3 個 API · 屬於 owners 區域」，數字取自既有圖，點各項可跳到右側欄對應標籤。

驗收：單元測試涵蓋分組規則（控制器／網址前段／根路徑／無 handler）與決定性；E2E 驗證區域視圖篩選與還原、摘要行數字與右側欄一致；petclinic 唯讀觀察寫入報告。

### WP36　按鈕總表（看懂「有哪些按鈕、做什麼」）

1. 頂部列主要切換由「畫面｜API」擴充為「**畫面｜按鈕｜API**」。
2. 「按鈕」頁為整個專案的**可操作項目總表**（按鈕、連結、送出、下拉等；輸入欄位預設收合為「欄位」群）。欄位：所在畫面、按鈕名稱（沿用 R5 名稱規則）、類型、動作摘要（前往「X」／送出到 Y／開啟彈窗／呼叫 API）、信心標示（僅在非「已確認」時顯示）、確認狀態。
3. 工具列：關鍵字搜尋（按鈕文字／畫面名稱／目的／API）、依區域、依畫面、依動作類型、依確認狀態篩選的晶片；排序可選（畫面、名稱、狀態）。
4. 點一列 → 切到該畫面的原型檢視並**高亮該按鈕**、右側欄顯示元素摘要；返回後保留總表的篩選與捲動位置。
5. 確認模式下每列右側有三態小按鈕（保留／移除／未確認），並提供**多選批次標記**（勾選列後套用）。批次標記對每一筆寫入既有的（畫面,元件）鍵，與逐筆標記**產出的 md 逐位元組相同**（以測試鎖定）。
6. 全站導覽的按鈕在總表中合併顯示為一列「（全站導覽）Home → Welcome ×9 個畫面」，展開可看每個畫面各自的決策並可個別標記；合併只是顯示，決策仍按畫面分開保存。

驗收：單元／E2E 涵蓋篩選、排序、批次標記與 md 位元組一致、點列跳轉與高亮、返回保留狀態、合併列展開；petclinic 觀察：總表列數與覆蓋率分類一致。

**WP34、WP35、WP36 完成後停止**，等需求方檢視（涉及主要導覽結構與資訊架構）。

### WP37　功能確認工作流（有效率地完成確認）

1. **進度總覽**：確認模式開啟時，頂部列顯示整體進度（例如「已確認 23／78 · 保留 18 · 移除 5」），點擊展開「確認儀表板」：依區域列出進度、尚未確認的數量與直接跳轉的連結。
2. **下一個未確認**：快捷鍵 `n`／工具列按鈕跳到下一個未確認的畫面或按鈕（順序：先依區域、再依畫面、再依元件，決定性）；到盡頭時提示「全部已確認」。
3. **鍵盤標記**：選取畫面或按鈕時，`k` 保留、`x` 移除、`u` 未確認；標記後預設自動前進到下一個未確認項（可在儀表板關閉自動前進）。快捷鍵說明列在「?」說明浮層。鍵盤事件不得在輸入欄位內觸發。
4. **影響預覽（不阻擋、只提示）**：標記「移除」時，右側欄即時顯示「這個決定的影響」，**全部由既有規則推導**：
   - 導向此畫面的其他按鈕／畫面（依已知關聯；沿用既有「保留元件導向移除畫面」衝突提示）。
   - 因此變成「可移除」的 API（沿用既有 `deriveApiUsage`，不得新增判定規則）。
   - 隨畫面移除的元件數。
   文字須註明「依已知關聯；靜態分析可能看不到外部或動態呼叫」。
5. **匯出前檢查**：按「匯出 md」先顯示摘要對話框（不改變匯出內容）：各狀態數量、移除清單、仍有衝突的項目、仍未確認的項目數與前幾筆；按鈕「仍要匯出」與「回去處理」。對話框可用「不再顯示」關閉（僅存於瀏覽器暫存）。
6. 既有的暫存提醒（換電腦／清除資料可能遺失）在儀表板與匯出前檢查中各出現一次。

驗收：E2E 涵蓋進度數字與決策一致、`n` 的順序決定性與盡頭提示、鍵盤標記（輸入欄位內不觸發）、自動前進開關、影響預覽三類資訊與既有衝突提示一致、匯出前檢查數字正確且**匯出的 md 與 R9 相同輸入逐位元組相同**。

### WP38　流程大綱、全域搜尋與首次引導

1. **流程大綱**：畫面右側欄與「功能」模式提供「從這裡出發」的可收合大綱：以選取畫面為根，列出已證據支持的前往關係，每條標示觸發的按鈕名稱，例如「Owner Details —[Edit Owner]→ Create Or Update Owner Form —[Update Owner]→ Owner Details（回到上一層）」。規則：只用非全站導覽的流程邊；深度上限 4、每層上限 8，超過顯示「還有 N 個」；循環以「（回到已出現的畫面）」標示不再展開；有歧義的目的並列全部候選；未解析目的標「無法確認的目的」。決定性。點節點跳轉到該畫面。
2. **全域搜尋**：頂部列加搜尋入口（`/` 或 `Ctrl/Cmd+K`），一個輸入框同時搜尋畫面（名稱、URL）、按鈕（文字）、API（方法、路徑）；結果依類型分組，點選跳轉並高亮目標。保留既有左側欄篩選行為。
3. **首次引導**：第一次開啟（瀏覽器暫存沒有紀錄時）顯示 4 步輕量引導卡片（瀏覽地圖 → 點畫面看完整頁 → 試操作 → 開確認模式標記並匯出），可略過、可從「?」說明浮層重新開啟；暫存不可用時每次都顯示但可略過。引導不遮擋功能，也不寫入決策。
4. 「?」說明浮層：快捷鍵清單、模式說明（操作／檢查）、狀態圖例（保留／移除／未確認、已確認／推定／未解析）。

驗收：流程大綱單元測試（深度／寬度上限、循環、歧義、未解析、決定性）；E2E 涵蓋跳轉、全域搜尋三類結果與跳轉高亮、引導出現／略過／重開、暫存不可用時行為。
