# ScreenTrace 第二輪調整指示（R2）

給 Codex 執行。執行前依 AGENTS.md §10 讀取 `AGENTS.md`、`docs/CODEX_INSTRUCTIONS.md`、`docs/REQUIREMENTS.md`、`docs/ARCHITECTURE.md`、`docs/ROADMAP.md`。需求原文在 REQUIREMENTS.md §1，**不得更動**；§2 決策 D1–D8 不得推翻。

## 0. 背景與目標

M1–M4（WP0–WP10）已完成，測試全綠（208 Java／40 JS／40 viewer／33 capture／26 E2E chromium）。審查者實際開啟 `struts1` 合成專案產出的報表，對照需求原文，發現**後端分析與 md 匯出大致符合，但報表呈現與需求原文有落差**。本輪只處理呈現層落差，不改分析正確性、不新增框架支援。

操作報表的是**非工程師的需求方**。任何需求方會看到的畫面，不得出現 JSON 原文、內部 ID、解析器類別名稱、markdown 反引號。

## 1. 工作包

每個工作包獨立提交；提交說明列出原因與受影響檔案。每個工作包完成後跑完整測試再進下一個（指令見 §3）。

### WP11　聚焦畫面的關聯線（最高優先）

需求原文：「點選畫面聚焦在選取的畫面，畫面四周透過關聯線連往畫面外呈現聚焦的畫面可以前往的其他畫面，hover 在關聯線上會顯示即將前往的畫面 url 和縮圖，點擊該條關聯線可以直接前往該畫面。」

現況：聚焦後只在預覽旁列出「→ 目的畫面」按鈕（`screentrace-viewer/src/relations.ts` 的 `focusRelation`），沒有線；總覽畫布才有線。

要求：
1. 聚焦畫面時，中央顯示該畫面預覽，**四周**（上下左右分配）放置可前往的目的畫面節點（外部節點用縮圖或畫面名稱卡片），以**實際繪製的連線（SVG）**從聚焦畫面連到每個目的節點。
2. hover／鍵盤 focus 在**線上**（含足夠的點擊命中區，例如透明粗線）顯示：目的畫面名稱、目的 URL、縮圖（有則顯示，無則顯示「無縮圖」）、觸發此關聯的按鈕名稱（沿用現有 `relationTooltip` 內容，可重用）。
3. 點擊線或目的節點 → 聚焦到目的畫面；「返回上一個畫面」仍可用。
4. 同一目的畫面有多條關聯時合併成一條線並在 tooltip 列出全部觸發按鈕；自我關聯（page → page）以迴圈線顯示，不可被省略。
5. 目的畫面很多（>12）時須可用，不得重疊到無法點擊：允許分群、捲動或「顯示更多」，但每個目的畫面都必須能到達。
6. 無關聯的畫面要顯示「沒有可前往的畫面」。
7. 保留未解析關聯：靜態無法證明的目的以虛線／標示「未解析」呈現，不得悄悄省略（AGENTS.md「Do not silently guess」）。

驗收：viewer 單元測試涵蓋線數量 = 去重後關聯數、tooltip 內容、點擊導向；E2E（至少 chromium）實際 hover 線並斷言 tooltip 出現 URL；點擊線後聚焦畫面改變。

### WP12　右側欄改為需求方可讀

需求原文：「畫布右側列出該畫面的資訊，包含呼叫的 API、各個按鈕。點擊右側欄位 API 或按鈕可以展示 API 或按鈕的資訊。」

現況：右側欄把路由、來源、證據以 JSON 文字顯示；行為顯示為 `a (UNRESOLVED)`、`review-button (CONFIRMED / UNRESOLVED …)`；載入時呼叫與元件觸發的呼叫幾十筆平鋪，看不出哪個按鈕對應哪個 API。

要求：
1. 版面分區：**畫面摘要**（名稱、主要 URL、來源檔）→ **按鈕與可操作項目** → **呼叫的 API** → **彈窗** → **資料檢核** → **技術細節**（摺疊，預設收起，才可出現 JSON／證據／解析器／信心）。
2. 按鈕與可操作項目：每筆顯示人看得懂的標籤（按鈕文字 → 無文字時用 value／title／name／id 的順序後備，最後才用元件類型 + 序號）、類型（按鈕／連結／下拉／送出表單…）、動作摘要（前往某畫面／呼叫某 API／開啟彈窗／送出表單）、確認狀態。重複的內部名稱（如多個 `a`、`page`）須可分辨。
3. 點按鈕 → 展開該按鈕資訊：觸發的動作、目的畫面（可點）、呼叫的 API（可點）、檢核規則、樣式（沿用既有點擊預覽元素的樣式資訊）、來源檔與行號。預覽中對應元素同步高亮。
4. 點 API → 展開方法、路徑、處理器、契約，並列出「被哪些按鈕觸發」。
5. 「載入時呼叫」與「元件觸發」分組並用中文說明；相同 API 去重並顯示次數。
6. `UNRESOLVED`／`AMBIGUOUS` 以中文標籤（未解析／有多個候選）與圖示呈現，不直接顯示英文列舉，並附一句需求方可理解的說明。
7. 技術細節摺疊區保留既有全部資料（可追溯性不可丟失）。

驗收：快照或 DOM 測試斷言預設可見區域**不含** `{`、`"source"`、`CONFIRMED`、`UNRESOLVED` 英文列舉、內部解析器名稱；斷言按鈕標籤不重複為 `a`；斷言點按鈕後出現其 API 與目的畫面。

### WP13　API 頁直接呈現「畫面 → 按鈕」

需求原文：「API 提供給後端人員，列出所有 API，清楚呈現 API 在哪些畫面及哪些按鈕被呼叫。」

現況：API 表只顯示呼叫來源數量，需點進去才看到來源。

要求：
1. API 列表每列直接顯示呼叫來源摘要（前 3 筆「畫面名稱 › 按鈕名稱」，其餘「＋N」可展開）；載入時呼叫標「畫面載入」。
2. 展開／詳情顯示完整來源清單，每筆可點回對應畫面並高亮按鈕。
3. 提供篩選：狀態（既有）、方法、關鍵字（路徑／畫面名／按鈕名）。
4. 「未被使用」列要有一句固定說明：僅表示未偵測到呼叫，不可直接刪除（沿用 D5 與使用指南措辭）。
5. 同路徑多處理器（目前 `/mapping.do` 出現多列）須讓使用者看得出差異（處理器名稱／HTTP 方法／來源），不可看起來像重複 bug。

驗收：測試以 fixture 斷言某 API 列文字含其呼叫畫面與按鈕名稱；篩選正確；點來源跳轉正確。

### WP14　review 模式標記範圍與介面

需求原文：「review 模式中可以標記畫面及按鈕為保留或刪除，不做任何記號則為未確認。」

要求：
1. **先查證再改**：確認目前標記選單涵蓋哪些元件類型。需求要求的最小集合是「畫面」與「按鈕」；按鈕包含 `<button>`、`<input type=button|submit|image>`、`<a>` 連結型操作、Struts `html:submit|button|cancel`。其他元件（表單、輸入框、表格）可標記也可不標記，但**不得因為只能標記少數類型而讓任何按鈕無法標記**。把查證結果寫進 `docs/reports/R2.md`。
2. 預覽中的按鈕可直接點選後標記（不必只從右側選單），已標記的按鈕在預覽上以顏色／標籤顯示保留（綠）、移除（紅）、未確認（灰）；畫面卡片同樣顯示狀態。
3. 提供批次操作：「此畫面所有按鈕標為保留／移除／未確認」。
4. 統計列顯示：畫面 保留／移除／未確認 數量、按鈕 保留／移除／未確認 數量。
5. 既有行為不得改變：決策按 (screenId, componentId) 保存；畫面移除時按鈕顯示「隨畫面移除」；API 可移除需所有來源皆移除（D4）；md 匯出／匯入往返不變。

驗收：測試覆蓋各類按鈕可標記、批次、統計；md 往返測試維持通過，格式版本不得無故升級（若必須升級，更新 `REVIEW_MD_CONTRACT.md` 與 schema 並寫 ADR）。

### WP15　左側欄與雜訊清理

1. 元件庫摘要（`library-ui.ts`）不得顯示原始反引號，不得把 markdown 當文字；摘要移到次要位置（摺疊區或底部），**畫面／API 切換、搜尋、檔案結構、確認模式放在最上方**。元件庫摘要中的 sha 雜湊預設隱藏（放技術細節）。
2. 畫面顯示名稱：優先使用 JSP `<title>`、頁面最顯著標題（h1）、Struts／Spring 的畫面識別，最後才用檔名；仍保留檔名與 URL 作為副標。名稱衝突時加路徑區分。
3. 預覽雜訊：預覽中殘留的未解析 JSP／EL 運算式（`${...}`、`<%= ... %>`）不得以原文直接出現在需求方可見的預覽中；改為不顯眼的佔位（如灰色「動態內容」徽章），原文放技術細節。**不可更動被分析專案原始碼**，僅改預覽輸出（`screentrace-capture/preview-markup.mjs` 一帶）。
4. 診斷列表（目前一長串 `JSP_UNRESOLVED / …` 重複代碼）改為依代碼分組計數（`JSP_UNRESOLVED ×11`），可展開看明細，並附中文說明。
5. 窄視窗（約 800px 寬）下三欄不得擠到無法使用：側欄可收合，或改為上下堆疊。

驗收：DOM 測試斷言沒有反引號、沒有未處理 `${` 出現在預覽可見文字；診斷分組計數正確。

### WP16　查證項目（只查證，必要時修）

以下項目審查者**未能驗證**，請查證、截圖或寫測試，結果記入 `docs/reports/R2.md`，失敗才修：
1. **元素樣式**（需求：「分析畫面中所有元素的樣式」）：點預覽中任一元素是否顯示樣式？涵蓋範圍（computed 或宣告？外部 CSS？inline？）有多完整？缺漏要列明。
2. **檔案結構＋實際 URL 搜尋**：以 `/orders/7` 對 `/orders/{id}` 的比對、`.do` 後綴、context path 前綴各一個測試。
3. **四種框架逐一在 chromium 開報表**，各自走一次：總覽 → 聚焦 → hover 線 → 點按鈕 → review 標記 → 匯出 md → 匯入 md。目前只有 struts1 被人工檢視。
4. **大專案可用性**：用腳本產生一個 150 畫面、600 個關聯的合成圖餵給 viewer，記錄總覽載入時間、聚焦切換時間、搜尋回應；超過 3 秒者列為問題，**只記錄，不做效能工程**（維持 WP10 範圍紀律），除非根本無法使用。

## 3. 測試與完成條件

每個工作包提交前執行：

```bash
mvn -B clean verify
npm --prefix screentrace-js test

npm --prefix screentrace-viewer test
node --test screentrace-capture/docs-baseline.test.mjs screentrace-capture/safe-files.test.mjs screentrace-capture/spring-resource-mappings.test.mjs screentrace-capture/capture-static-jsp.security.test.mjs screentrace-capture/preview-markup.test.mjs screentrace-capture/preview-v2.test.mjs screentrace-capture/pack-preview.test.mjs
node --test screentrace-viewer/test/*.e2e.mjs
```

基線：208 Java／40 JS／40 viewer／33 capture／26 E2E，只增不減。

全部完成條件：
1. WP11–WP15 驗收條件全數通過，WP16 結果寫入 `docs/reports/R2.md`。
2. 更新 `docs/ROADMAP.md`（新增 R2 列與狀態）、`docs/USER_GUIDE.md`（新操作方式；截圖若改變須重拍 `docs/images/user-guide/`）、`docs/ARCHITECTURE.md`（若 viewer 結構有變）。
3. 單一 HTML 仍可離線開啟（D6）；不新增外部網路依賴；`file://` 開啟可用。
4. 重新產生四個 fixture 的報表，**決定性**測試（兩次輸出逐 byte 相同）仍通過。

## 4. 停止條件

- 任一工作包的驗收無法達成，或發現需要改 schema／分析邏輯：**停止並寫入 `docs/OPEN_QUESTIONS.md`**，等待需求方確認，不要自行猜。
- 完成後**停止**，不要自行開始新工作包；回報：每個 WP 的提交、測試數字、`docs/reports/R2.md` 位置、尚未解決項目。
