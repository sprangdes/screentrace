## 沿用的作法

- **每一輪一個 PR**，只推送到指定分支。PR 合併後，先執行 `git checkout -B <分支> origin/main`，再開始下一輪。
- **一律以 merge commit 合併**，合併前要取得使用者明確的同意（使用者回覆「合併」）。
- **先提案、確認後再實作**：每輪開始時先盤點、量測，提出做法與待決定的事，使用者確認後才動手。
- **文件**：
  - 每輪寫一份 ADR，並在 [ADR 索引](adr/README.md) 加一列。
  - ROADMAP 結尾加一節。
  - 更新 HEALTH_CHECK 的總表與進度。
- **排版與檢查**：
  - Java：`./mvnw com.diffplug.spotless:spotless-maven-plugin:apply`
  - TS／JS 排版：`npm --prefix screentrace-viewer run format`
  - JS lint：`npm --prefix screentrace-viewer run lint`
  - TS：viewer 建置時的 `tsc`
- **行為不變的驗證**：
  - 以修改前的版本（worktree）與修改後的版本，分別用 CLI 分析 `fixtures/` 的 15 個專案，比對產物（共 277 個檔案，其中 `struts2-rejected` 依設計會失敗）。
  - 效能類的修改另外用 80 個畫面的合成專案比對。合成專案不進版控，產生方式見下一節。
  - worktree 切換 commit 後，必須重新建置 viewer（`npm ci`、`npm run build`）與 jar，否則報表會因為舊的 `viewer.js` 而不同。
- **行為改變的驗證**：新測試要在修改前的版本失敗、修改後通過。如果只是因為缺少新類別而失敗，要在紀錄中照實說明。
- **CI**：四個 job（build-and-test、windows、dependency-audit、node-dependency-audit）。
- **PR 追蹤**：開 PR 後訂閱 PR 活動，並排一次約 50 分鐘後的補查；CI 全綠後取消補查，詢問使用者是否合併。

## 量測工具（sandbox）

- 包一層 `node` shim 放在 PATH 前面，記錄 `capture-static-jsp.mjs`、`pack-preview.mjs`、`cli.mjs` 的耗時。
- CLI 執行方式：`java -Dscreentrace.home=<版本目錄> -Dscreentrace.js.module=<版本目錄>/screentrace-js/cli.mjs -jar <版本目錄>/screentrace-cli/target/screentrace-cli-0.1.0-SNAPSHOT.jar analyze <專案>`。輸出位置是 `<home>/analyze/<專案名>`，每跑完一個專案要先搬走，因為 `wp10/` 底下有同名的專案。
- 合成專案：用腳本產生 80 組 Struts action，每組含一個 JSP（40 列表格、表單、前後頁連結）、一個 Action 類別（20 個方法）與一個 Form 類別。
- 找 Java 熱點：`-XX:StartFlightRecording=settings=profile`，再用 `jfr print --events jdk.ExecutionSample` 依方法彙總取樣。

## Sandbox 注意事項

- 執行 Maven 時設定 `LANG=C.UTF-8 LC_ALL=C.UTF-8`。離線模式（`-o`）缺少 clean 與 surefire 外掛時，改用線上模式跑一次。
- `node_modules` 不在版本控制中，新的 container 要先對三個套件執行 `npm ci`，並建置 viewer。
- `screentrace-js` 的測試要在該目錄執行（`npm --prefix screentrace-js test`），在根目錄執行會有 1 個測試因為相對路徑而失敗。
- viewer E2E 的 `performance.e2e.mjs` 在 sandbox 會因時間門檻失敗，CI 上會通過。
- 最近一次的本機結果：Maven 600 個（595 通過、5 略過）；JS 180、capture 93、viewer 單元 148 個全部通過。
