# ADR 0058：全專案功能區域依據與按鈕列操作摘要

- 狀態：已接受（2026-10-05）
- 關聯：OQ-020、R10 WP35/WP36 修正

## 背景

WP35 原實作先按控制器／Action 分組，缺少 handler 時再按 URL 分組。PetClinic 因此有五個單畫面區域，eMusicStore 有三個；一份報表同時混用兩種依據，也讓區域名稱暴露 `Controller` 與 `View Controller` 等技術字樣。WP36 的長動作摘要混合了主要動作、候選結果及伺服端路由，確認模式的逐列標記也缺少快捷控制。

需求方已決定以同一個全專案依據分組：網址前段、控制器類別、JSP 目錄。系統計算各依據下只含一個畫面的區域數，選最少者；平手依網址、控制器、JSP 目錄排序。功能區域介面可切換依據並顯示目前選項。區域名稱人性化並移除 Controller、View Controller 等後綴。

## 決策

`chooseFeatureGroupingBasis` 與 `groupFeatureRegions` 為唯一分組純函式；每個策略都對整個專案套用同一規則。無法從該依據證明分組值的畫面進入同一個「首頁與其他」組，不混用第二依據補值。所有排序使用穩定的字串順序。此修正不變更圖、分析器、端點、API 狀態或 review-state schema。

按鈕列拆成「主要動作」與「可能的結果」。連結只呈現「前往「X」」；表單顯示「送出表單」，以固定順序列出目的畫面，伺服端路由只在預設收合的技術細節中呈現。多個畫面候選會標明有多個可能結果。列依畫面、固定操作類型順序、名稱排序。確認模式下每個畫面元件列提供保留／移除／未確認快速操作，沿用 `(screenId, componentId)` 複合鍵及 `setComponent`；保留批次操作。全站共用列展開後按畫面提供各自的三態操作。逐筆、快速及批次標記共用狀態寫入，md 輸出仍以既有 review state 產生。

「有多個可能結果」以不同的畫面結果候選計數；伺服端路由不會額外偽裝成第二個畫面候選。若只有路由、沒有可證明的目的畫面，結果顯示「可能前往：靜態分析無法確認」，完整路由仍在收合技術細節內。

按鈕與 API 頁未選項目時收合右側資訊欄；按鈕頁切回一般畫面清單，不把功能區域卡片放在左欄。按鈕表格的類型與確認狀態不逐字換行；確認狀態與「查看按鈕」分欄顯示。功能區域在確認模式關閉時不產生確認進度文字或控制項。

## 測試與斷言調整

先提交紅測試 commit `3cb7d91`、`16d2f26` 及 `f78e335`。在舊實作上，功能區域策略選單／統一依據、按鈕頁左欄收合、主要動作與候選摘要等測試失敗；路由候選在舊摘要中呈現「可能結果：伺服端處理」，新測試要求保留未解析畫面目的並將伺服端路由收合，該測試先於對應程式修正提交並已確認失敗。修正後同測試通過。新增測試鎖定策略自動選擇、平手順序、名稱後綴清理、候選排序、路由摺疊、三態寫入、右欄收合及欄位不折行。

OQ-020 授權並要求替換的既有 WP35 預期如下：

| 測試 | 舊預期 | 新預期 | 原因 |
|---|---|---|---|
| `wp35-feature-regions.test.mjs` 第一項 | 預設按控制器／Action 分區，部分無 handler 畫面使用「首頁與其他」備援標籤；名稱保留 Home Controller、Owner Controller | 對全專案選一個依據；fixture 自動選網址前段，Owners 兩畫面、首頁與其他含 root 與 missing；明確選控制器時移除技術後綴 | OQ-020 取代控制器優先及逐畫面退補規則 |
| `wp35-feature-regions.test.mjs` 第三項 | 「首頁與其他」名稱同時被當成分組依據 | 所有區域依據都顯示網址前段；未知值仍歸同一備援區 | 顯示依據要代表整專案所選策略 |
| `wp35-feature-regions.test.mjs` 第四項 | 顯示 `Mvc View Controller` | 顯示 `Mvc` | 移除 View Controller 技術後綴並維持可讀名稱 |

其餘既有斷言未修改。追加的 E2E 檢查連結摘要不含「呼叫 API」或「送出到」、候選順序、快速標記、按鈕類型／狀態不折行、右欄收合及確認模式關閉時不顯示進度。

## 取捨

最少單畫面區域不必然代表最符合業務語意；因此保留明確依據切換，預設演算法只按需求方指定的 singleton 數與平手順序決定。未知依據值集中在「首頁與其他」，不根據另一依據猜測。表格允許在自身捲動區水平捲動，以維持關鍵欄位可讀且不逐字折行。
