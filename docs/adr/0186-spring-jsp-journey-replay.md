# ADR 0186 Spring JSP 操作回放：正常流程、請求模式與流程延續

## 背景

以 insure 逐一點擊報表中的所有操作後，與真實系統仍有落差：

- 登入、查詢申請、查詢保單、填寫資料、返回修改資料等請求都要使用者在「成功頁」與「錯誤頁」之間選擇；真實系統在資料正確時直接前往下一步。
- 新投保與續保共用同一組 JSP（試算、填寫、確認），只以 `empty quote.previousId` 這類條件切換標題、返回連結與唯讀欄位。報表只有一個畫面，續保流程會回到新投保的頁面，返回連結也要使用者選擇。
- 元素本身被 `<c:if>` 包住時，點擊它仍跳出只有一個選項的「條件尚未求值」選單；多目的選單把 URL 運算式當成條件。
- 後台核保後的「已更新核保狀態。」沒有顯示。

## 決定

- **正常流程。** `SpringControllerReturns` 對沒有 `if`、`catch`、`switch`、迴圈或 lambda 包覆、也不是條件運算式分支的回傳加上 `SpringMainPath` 證據（記錄所屬方法）。私有 helper 的回傳只有在呼叫本身也是正常回傳時才算。報表只採用所點擊端點之 handler 自己的證據；正常流程的目的唯一時直接前往，並在狀態列列出其他可能結果。表單仍檢查必填核取方塊。
- **請求模式。** `SpringRequestVariants` 依 handler 回傳路徑推出模型物件屬性是否為空：`new T()` 採 T 的字面欄位初值；專案方法建立 `new T()` 並以 `@PathVariable` 傳入的參數呼叫 `setP(...)` 時，P 為非空。某屬性在不同回傳路徑上分別證明為空與非空時，所有以 `empty 模型.該屬性` 判斷的 JSP 頁各分為兩個畫面（沿用 `stateVariant`／`stateVariantOf`，名稱取自頁面 `<h1>` 依模式解出的文字）。已證明的 RENDERS 指向對應模式；無法證明的回傳（例如由表單送回的資料）同時連到兩個模式。畫面記錄 `requestProperty` 與 `requestFacts`，`JspScreenFacts` 與預覽以此判斷元件歸屬、條件連結與文字。
- **流程延續。** 報表模擬依本次瀏覽歷程中最近一個有請求模式的畫面，在同一頁的兩個模式間保留相同模式（例如續保流程的確認頁返回修改後仍是續保填寫頁）。這只用於兩個模式都可能的結果。
- **元素自身的條件。** 點擊的元素若與其 JSP 守衛相同，視為條件已成立，不再顯示單一選項的條件選單。
- **條件式 URL 的選單文字。** 多目的選單依 `JspConditionalUrl` 的守衛標示各選項（「當 empty quote.previousId」／「其他情況」）。
- **成功訊息。** 成功轉址的 flash 訊息也接受 `try { …; addFlashAttribute("success", …) } catch { … }` 之後的轉址；JSP 狀態轉換的模擬顯示該訊息。
- 畫面名稱含狀態或模式時，模擬選項與狀態列沿用該名稱。

## 限制

- 正常流程是靜態結構的判斷，不代表輸入一定有效；錯誤與保護分支仍列在狀態列與 API 頁。
- 請求模式只處理字串屬性的空與非空，且只追一層專案方法。
- 流程延續假設同一流程延續同一筆資料，不追蹤資料識別；不同申請之間切換時以狀態切換器調整。
- 登入頁的後台導覽列依工作階段屬性顯示，報表尚未推論過濾器設定的工作階段事實；試算頁「改試算機車／汽車」的文字依網址參數，預覽仍顯示預設值。

## 驗證

`spring-jsp.test.mjs` 檢查成功轉址只有正常分支帶 `SpringMainPath`，以及 `new Draft()` 與 `renewal(@PathVariable id)` 產生兩個模式畫面、RENDERS 指向與元件歸屬。insure 以腳本完整操作：新投保（試算→填寫→確認→送出→核保通過→模擬繳費→出單→保單查詢）、續保（查詢→明細→續保試算→填寫續保資料→確認續保申請→返回修改→送出）、後台（登入→總覽→待核保→開始核保→核保通過／不通過→返回→登出），每一步都直接到達真實系統的對應頁面。
