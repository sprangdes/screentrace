# ADR 0143：R52 預覽擷取上限依畫面數放寬，Java 不導入 Error Prone

## 背景

[HEALTH_CHECK_20261111](../HEALTH_CHECK_20261111.md) 留下兩項待決定的事，需求方請開發方依建議處理。

- **擷取上限**：CLI 等待預覽擷取（`capture-static-jsp.mjs`）的時間固定為 120 秒，超過就結束程序，所有畫面都沒有預覽。R47 前，80 個畫面的合成專案就因此失去全部預覽。R47 把同一專案降到 48.7 秒（完整 CLI 中約 52 秒），但每個畫面仍要約 0.6 秒，數百個畫面的專案還是會超過上限。
- **Java lint**：R49 盤點 `javac -Xlint:all` 有 79 個警告，大多是泛型 varargs 與 deprecated API 的雜訊（ADR 0140 R49-4）。

## 決定

- R52-1：擷取上限改為 `120 + 2 × 畫面數` 秒，最多 30 分鐘（`ScreenTraceCli.captureTimeoutSeconds`）：
  - 畫面數取自分析圖的 SCREEN 節點。
  - 每個畫面多給 2 秒，約是 R47 後實測值的 3 倍，保留給較慢的機器。
  - 30 分鐘的上限，避免擷取卡住時 CLI 無限期等待。
  - 逾時的警告會寫出這次使用的秒數。
- R52-2：預覽封裝（`pack-preview.mjs`）維持 120 秒。80 個畫面只需約 0.5 秒，沒有放寬的需要。
- R52-3：Java 不導入 Error Prone，也不把 `-Xlint` 警告設為錯誤。理由：
  - Error Prone 需要另外設定 javac 的 `--add-exports` 等參數，Windows CI 也要一起驗證。
  - 目前 79 個警告沒有一個是實際的 bug。
  - 排版（Spotless）、空 `catch` 的檢查（ADR 0141）與完整測試已經擋住主要風險。
  - 日後若遇到這類工具能防止的實際 bug，再重新評估。

## 後果

- 大型專案的預覽不會再因固定 120 秒而整批失去。代價是擷取卡住時，CLI 最多會等 30 分鐘才結束。
- 驗證：
  - 新增 `CaptureTimeoutTest`：0、1、80、500、840 個畫面與負數的上限值。它在修改前的版本無法編譯，因為方法不存在。
  - 15 個 fixtures 的產物與修改前逐位元組相同。
  - Maven 600 個（595 通過、5 略過）。
