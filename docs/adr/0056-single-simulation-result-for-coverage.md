# ADR 0056 — Single simulation result for element coverage

- Status: Accepted
- Date: 2026-10-05
- Context: R7 OQ-019 found that a submit control's actual click delegates to its associated form, while coverage previously assessed the control as an isolated button. PetClinic's Find Owner and Add Visit therefore worked in the simulation but were counted as unsupported.
- Decision: Use `simulateElement` as the element-level entry point for user actions, coverage, and explanations. It resolves native submit buttons, submit/image inputs, and externally associated forms through the DOM's `form` association. The returned effect carries its `simulatable` result and optional reason; `canSimulate` is a compatibility accessor for that returned value only. Cause categories are projected from the same result. No project-specific or element-type exception is introduced.
- Coverage display: Count supported elements whose delegated simulation result carries `BEHAVIOR_AMBIGUOUS` and more than one returned choice, and show that count parenthetically beside supported behavior. This reads the same simulation result and its delegation metadata; it adds no eligibility decision. The count measures supported delegated controls that expose multiple behavior candidates, not all multi-screen choices presented by a form.
- Authorized existing assertion updates (all other assertions and fixtures remain unchanged):
  - `screentrace-viewer/test/wp26-simulation.e2e.mjs`, test `WP26 ${engine}: offline actions, all candidates, native validation, popup, API and reset preserve md`: old expected coverage `5 / 3 / 5`; new expected coverage `6 / 3 / 4`. The submit button now shares its owning form's two proven outcomes, so one element moves from unknown to simulatable; total elements and editable fields are unchanged.
  - `screentrace-viewer/test/wp26-feedback.e2e.mjs`, test `WP26 feedback: human result strip, collapsed complete proof, mode-specific detail and disjoint coverage`: old expected coverage `5 / 3 / 5`; new expected coverage `6 / 3 / 4`, for the same form-delegation behavior.
- Old-implementation evidence: With both authorized assertions updated and the old bundled viewer still in the test fixture, Chromium produced `此畫面：有圖支持的行為 5 個；可直接輸入的欄位 3 個；無法確認 5 個`; both assertions failed against expected `6 / 3 / 4`. Rebuilding the viewer caused both tests to pass. The five WP29 submit-consistency tests also failed on the prior implementation and pass after this decision.
- Verification: `npm run build`; viewer unit tests (80 passed); targeted Chromium E2E (9 passed, including both WP26 cases and all five WP29 family fixtures).
- Result: The WP29 initial values 57 / 85 supported, 17 unknown, and four ambiguous unknowns were manually reclassified from the earlier actual 55 / 85 and 19 unknown run; they were not a fresh CLI run and were wrong. The four shared Add/Update Pet/Owner submit controls also return supported selectable outcomes through the shared simulation entry point. Fresh analyze/report output now gives PetClinic 61 / 85 supported, 11 editable fields, 13 unknown (11 no known behavior, two unresolved destinations, zero ambiguous and zero unsupported), including four supported controls with multiple behavior candidates. Find Owner and Add Visit remain supported. The two XML/JSON links whose data endpoints have no proven screen destination remain unknown. eMusic remains 28 / 128 supported, 13 editable, 87 unknown (72 no known behavior, 15 unresolved destinations), with zero multiple-candidate controls.
- Verification of the new parenthetical display: a new Chromium E2E fixture with an ambiguous form action failed against the previous viewer bundle because the label omitted the candidate count; after implementation it reports one supported control with multiple candidates. Complete verification for this correction: Maven clean verify (268 tests), viewer unit (80), screentrace-js (40), and Chromium E2E (85), all passed.
